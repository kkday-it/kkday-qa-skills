# Dev Focus Alignment

動工前強制對焦。在寫任何一行 code 之前，先輸出以下五段清單給人類確認，得到回覆才動工。

## 為什麼要做這件事

LLM agent（包括人類工程師）拿到需求最常見的失敗模式：

1. **腦補需求** — 把「加個 modal」自動延伸成「順便重構整個對話流」
2. **改錯檔案** — 修改了不在原本意圖內的位置，產生意外副作用
3. **事後解釋成本** — 沒對焦就動，事後 PR review 階段才發現方向錯，回不去
4. **跨人 / 跨 agent 期望落差** — 出題的人想的、動手的人做的、驗收的人期待的，三個版本

對焦清單**強迫**把腦中的隱含假設外顯化，讓人類有機會在低成本時喊停。

## 執行流程

收到需求後：

1. **先讀相關程式碼**（不要憑記憶猜）
2. **輸出對焦清單**（下方範本）
3. **停下來等人類回覆**
4. 得到「OK / 改 X / 不對方向」的明確回應後才動工

如果第 1 步發現需求本身有歧義 → 對焦清單裡明確列出「需要釐清的點」，不要自己決定。

## 對焦清單範本

```markdown
## 開發對焦

### 1. 需求理解
[用一句話說明你理解的需求]

### 2. 會動到的檔案
- `path/to/file_a.ext` — [做什麼改動]
- `path/to/file_b.ext` — [做什麼改動]

（如果跨多層 / 多模組，分組列出，例如：）
- 後端 / API 層
  - `...`
- 前端 / UI 層
  - `...`
- 資料層 / DB / migration
  - `...`

### 3. 實作方向
[簡述技術方案，1-3 句話。重點是「為什麼這樣做」，不是 step-by-step]

### 4. 影響範圍
- [會不會影響其他功能 / 既有使用者？]
- [有沒有 DB schema 變動？需要 migration？]
- [上下游 type / interface 是否需要同步？]
- [是否需要更新 docs / changelog？]

### 5. 潛在風險
- [列出可能的 breaking change、edge case、不確定的設計決策]
- [如果你發現任何「需要人類拍板」的選擇題，在這裡列出，不要自己選]

---
確認後開始實作。
```

## 五段為什麼是這五段

| 段 | 防的失敗模式 |
|---|---|
| 1. 需求理解 | 把需求重述一遍，揪出「我以為他要 X 結果他要 Y」的歧義 |
| 2. 會動到的檔案 | 防止改超出範圍；也讓 reviewer 提前知道 PR 範圍 |
| 3. 實作方向 | 強制把「為什麼這樣做」說出來，避免無腦複製貼上現有 pattern |
| 4. 影響範圍 | 揪出隱性 coupling — 改 A 會不會壞 B |
| 5. 潛在風險 | 把「我不確定」明確化，把選擇題丟回給有 context 的人 |

## 何時跳過對焦

很少。但有少數情境可以略過：

- **trivial fix**（typo、格式、單行 import 修正）— 直接做，commit message 寫清楚即可
- **explicit fast-track**（人類明確說「這個直接做不用對焦」）
- **dry-run / readonly 行為**（只讀分析、不改檔案）

但 **DB migration、API breaking change、跨服務改動、>3 個檔案的改動** 一律不可跳過。

## 跟 task-input-readiness-check 的順序

兩支 meta skill 在「動工前」都會跳出來，分工如下：

```
task-input-readiness-check    →    dev-focus-alignment    →    動工
       (input pre-flight)              (方向對焦)
```

- **task-input-readiness-check**：先檢查「動工的素材齊不齊」（spec / target / env / 帳號），缺項就停下索取
- **dev-focus-alignment（本 skill）**：素材齊備後，再列「方向對不對」的對焦清單給人類確認

**為什麼分兩支不合併**：兩道門的失敗模式不同。
- input 缺 = agent 沒材料，做了也白做（解法：跟人類索取）
- 方向錯 = agent 有材料但理解錯（解法：把腦中假設攤開給人類驗）

合成一支會讓「索取資料」和「確認方向」混在一塊，人類看不清楚要回什麼。

**對 agent 的執行原則**：兩支都跳出來時，**依序執行不重複**：
1. 先跑 task-input-readiness-check，input 齊備
2. 再跑 dev-focus-alignment，方向對焦
3. 兩道綠燈才動工

人類只會被打斷兩次（一次補資料、一次確認方向），不會被反覆問同樣的事。

## 跨人 / 跨 agent 怎麼用

對焦清單是一份「**可轉手的對齊紀錄**」，不只給寫 code 的人自己看。常見三種接力場景：

- **出題的人 → 動手的人**：出題方寫的 task spec / 需求文件可以**直接當對焦清單第 1-3 段的輸入**，動手方補第 4-5 段、回傳給出題方確認方向才動工
- **動手的人 → review 的人**：對焦清單放進 PR description，reviewer 對著清單看 PR 比看 raw diff 快得多
- **agent 自我迴圈**：如果在多輪 agent loop 內，把對焦清單寫進 progress 檔案，下一輪 agent 知道前一輪確認了什麼，不會重複對焦

> 不管你是一個人寫 code、或是在用 multi-agent 系統，這份清單都用得上 — 它的價值在「把腦中假設攤開」這個動作，跟有沒有特定角色設定無關。

## 反模式

- ❌ 對焦清單寫得太細，變成 step-by-step 實作計畫 — 那是動工後的事，這裡只到「方向 + 範圍 + 風險」
- ❌ 對焦清單寫完直接動工，沒等人類回覆 — 失去「低成本喊停」的機會
- ❌ 把「我會小心」當成風險評估 — 風險要寫具體事項
- ❌ 用對焦清單當免責聲明（「我列了風險所以後果不關我事」）— 人類核可後出問題仍是 author 責任
