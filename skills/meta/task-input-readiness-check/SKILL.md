# Task Input Readiness Check

任務啟動前的「必要 input 清單」檢查機制。**缺任一項就停下索取**。

## 為什麼

長任務最浪費 context 的失敗模式：

1. agent 一頭埋下去做
2. 做到第 30 分鐘發現缺某個 spec / token / branch
3. 中斷、跟人類索取、又花 5 分鐘重建現場才繼續
4. 或更糟：agent 自己腦補 / 隨便填，做出錯方向的成品

對 input 「pre-flight check」一次性把所有缺口在動工前曝光，讓人類補齊或明確拒絕，**永遠不要邊做邊缺**。

## 執行流程

收到任務後：

1. **判斷任務性質** — 屬於哪一類（API 開發 / 資料分析 / debug / retro / migration / ...）
2. **列出該類任務的必要 input**（下方有常見類別範本）
3. **逐項驗證齊備** — 對每項標 ✅ 已具備 / ⚠️ 缺失 / ❓ 不確定
4. **缺任一項 → 停下，回頭跟人類索取**，列出明確問題清單
5. **全部 ✅ → 列出對焦清單，得到 GO 後才開工**

第 4 步重點：**不要自己腦補**、**不要先做能做的部分**、**不要先動 code 等資料來再補**。動工的最低門檻是 input 齊備。

## 必要 input 範本（依任務類別）

實際 input 依任務類型而異，下面是常見類別參考。**改用前先檢視自己的任務上下文，加減項目**。

### 類別 A：開發 / 實作任務

| # | Input | 何時需要 | 缺了會怎樣 |
|---|---|---|---|
| 1 | 需求 spec / 設計文件 / 工單連結 | 動工前 | 不知道做什麼、靠對話片段拼湊容易漏 |
| 2 | 目標系統 / 目標 repo（含 branch） | 動工前 | 改錯地方 |
| 3 | 上下游 interface 定義 | 動工前 | 跟其他模組搭不起來 |
| 4 | 測試 / 部署環境（哪台 stage / sit）| 實作前 | 跑出來無法驗證 |
| 5 | 風格 / 慣例參考（既有相似實作） | 實作前 | 風格不一致、reviewer 必退 |

### 類別 B：測試 / QA 任務

| # | Input | 何時需要 | 缺了會怎樣 |
|---|---|---|---|
| 1 | 測試需求 / 測試情境文件 | 設計 case 前 | 測錯方向 |
| 2 | 目標系統 + 對應 RD repo / branch | 設計 case 前 | 反向 case 不知道驗證層在哪 |
| 3 | 測試環境（實例編號 / endpoint） | 執行 case 前 | 跑了等於白跑 |
| 4 | 測試帳號 / 測試資料 | 執行 case 前 | 跑到一半卡住 |
| 5 | 預期回報目標（Jira / Confluence / 其他） | 完成後 | 做完不知道交給誰 |

### 類別 C：分析 / Debug 任務

| # | Input | 何時需要 | 缺了會怎樣 |
|---|---|---|---|
| 1 | 問題現象描述 + 重現步驟 | 動工前 | 只能憑印象猜 |
| 2 | 相關 log / error message / stack trace | 動工前 | 沒有 entry point |
| 3 | 涉及的系統 / 服務 / 模組 | 動工前 | 找不到要看的程式碼 |
| 4 | 時間範圍（什麼時候開始壞） | 早期 | 找不到回歸點 |
| 5 | 是否有 reproducible 環境 | 驗證前 | 修了無法確認修好 |

### 類別 D：流程 / Workflow 任務（retro、release audit、metrics 收集...）

| # | Input | 何時需要 | 缺了會怎樣 |
|---|---|---|---|
| 1 | 範圍定義（時間區間 / 專案 / 團隊） | 動工前 | 抓資料抓不完 |
| 2 | 資料來源清單 + 存取權 | 動工前 | 撈不到資料 |
| 3 | 輸出格式 / 目標讀者 | 動工前 | 寫了不對胃口 |
| 4 | 完成標準（acceptance criteria） | 動工前 | 不知道何時叫做完 |
| 5 | 既有範本 / 過去類似產出參考 | 早期 | 風格不一致 |

## 索取資料時的格式

如果發現缺項，**不要只丟一句「資料不足」**。用以下格式給人類，讓他能一次補齊：

```markdown
## Input 檢查結果

### ✅ 已具備
- [item] — [從哪來]

### ⚠️ 缺失（必補才能動工）
- **[item]** — 缺什麼具體資料，預期是什麼形式
  範例：「目標 branch」 — 需要 RD 提供的 feature branch 名稱，可從 RD 工單或他直接告訴你
- **[item]** — ...

### ❓ 不確定（需要釐清）
- **[item]** — 不確定是否必要 / 是否已具備
  範例：「測試帳號」— 不確定本次測試是否需要登入態，請確認

---
請補上 ⚠️ 項目（❓ 項目可選），齊備後我會列對焦清單再進入實作。
```

## 跟其他 meta skill 的關係

- **task-input-readiness-check（本 skill）** → 動工前的 input 檢查（pre-flight）
- **dev-focus-alignment** → input 齊備後、動 code 前的對焦清單
- 兩者組合 = 「input 齊」+「方向對」雙重把關，再進入實作

## 反模式

- ❌ 列了 input 清單但全部都自己標 ✅，沒真的逐項驗證 — checklist 變裝飾
- ❌ 缺項時自己腦補預設值 — 該停就停
- ❌ 把「人類沒回覆」當成隱含同意 — 沒回覆 = 不知道、繼續等
- ❌ 把太多東西列為「必要」變成 over-gating — 真正的必要是「缺了動不下去」，nice-to-have 列在 ❓ 區
