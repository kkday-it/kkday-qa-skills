# Chat Mode — 回顧「當前這段對話」

job-retro 的第二種模式。用在**沒有本機檔案存取**的環境(claude.ai、Claude 桌面版聊天),
或使用者要回顧的就是「我們現在這段對話」而非某個 CLI 背景 job。

與預設(CLI / session-file)模式的差別:**輸入不是 transcript 檔,是對話本身**——
它已經在你的 context 裡。所以這個模式**不解析檔案、不碰 `~/.claude`、不執行任何腳本**,
直接「重讀我們這段對話」來分析。

> 怎麼選模式:能讀本機 `~/.claude/projects/*.jsonl`(有 Bash / 在 Claude Code)→ 用預設模式
> 跑 `scripts/extract_session.py`。否則(純 chat 環境,或要回顧當前對話)→ 用這個 chat mode。

## 流程

```
Step 1  確認對象:回顧「當前這段對話」還是使用者貼上的一段對話?
Step 2  重讀全程,標出四類修正訊號
Step 3  辨識角色與工作性質
Step 4  產出 retro(做了什麼 / 修正與根因 / 踩的坑 / 做對的 / lessons)
Step 5  沉澱:寫進記憶 / 輸出文字 / 產 Confluence(對外先確認)
```

## Step 2 — 重讀對話,標出四類「修正」訊號

核心一樣是「人類不斷修正的地方」,每一次都是「本來可以不發生的來回」。逐一掃過使用者發言:

- **interrupt(打斷)**:喊停、要你別做正在做的事。根因常是「動作太大沒先對齊」。
- **redirect(改方向)**:「不對 / 不是 / 改成 / 應該 / 其實 / 重來」——你走錯路。根因常是「需求理解偏差」或「沒先問就假設」。
- **question(困惑 / 釐清)**:反覆問同一件事。根因常是「你沒講清楚」或「文件缺口」。
  - 特例:**連問 2+ 次同一概念** → 當下就該停下來給一份整合說明,而不是零碎回答。
- **supplement(中途才補的輸入)**:丟進一開始沒給的資訊(文件、Figma、截圖、範例、情境)。**要再分兩種**:
  1. **漏給**:本該一開始備齊的必要輸入(例:要產測試 case,PRD / 驗收標準卻後來才補)→ 教訓:替這類任務建 **input 前置清單**。
  2. **刻意漸進**:使用者**故意**分段給,把產出帶往某種風格 / 觀點(例:先要 case,再補「要使用者情境 / 操作導向」)→ 記成**可重用的 prompt 技巧**,不是缺陷。
  - 判準:這資訊若一開始就給,第一版會不會就對?會 → 漏給;就算給了也只是不同風格 → 刻意漸進。

> 同時留意:重複重試、整段被推翻的死路、重複勞動——都是摩擦點。

(這四類與預設模式 `analysis-framework.md` 完全一致,只是這裡靠「讀對話」而非腳本標記。)

## Step 3 — 角色與工作性質

從對話主題、提到的系統 / 工具判斷 persona,分兩維:**領域(domain)** × **動作(mode)**。
細節同 `role-detection.md`(只是證據來源是對話內容,不是 cwd / MCP 統計)。

## Step 4 — 產出 retro

用 `analysis-framework.md` 的輸出格式(標題 / 結果 / 角色 / 做了什麼 / 修正與根因表 /
踩的坑 / 做對的 / Lessons)。**泛化,別過擬合**:每條 lesson 抽掉一次性細節,講「這類任務」的原則,
且能指回對話裡的具體段落。

## Step 5 — 沉澱

- **記憶**:環境有記憶功能(claude.ai memory / projects)就把 feedback 類教訓寫進去(附 Why + 下次怎麼套用)。沒有就**輸出成文字**讓使用者自己存。
- **Confluence / 工作紀錄**:依 `confluence-template.md`。發 Confluence 是對外動作,**先給使用者過目再建頁**。
- **prompt 技巧**:把「刻意漸進」類 supplement 收斂成一句可重用的下達指令範本。

知識回饋的去處與信心門檻,與預設模式共用 `knowledge-feedback.md`。
